# EarlyExperience on ToolSandbox (Standalone)

This project implements the **IL control, IWM followed by IL, and SR** using Apple ToolSandbox's environment and native evaluator. It does not require a separate pipeline, external memories, a skill library, or G000/G003 artifacts.

Status: standalone collection, dataset preparation, training, and evaluation code is implemented. Eleven offline tests pass, including real tool execution and the native evaluation entrypoint. Formal data collection, GPU training, and benchmark evaluation have not been run. Fixture scores are not experimental results.

## Methods and artifacts

| Method | Data | Training |
|---|---|---|
| IL | expert_sft.jsonl | Original model followed by expert-action imitation |
| IWM | iwm_sft.jsonl and expert_sft.jsonl | The same model first predicts observations, then continues with expert imitation |
| SR | reflection_sft.jsonl and expert_sft.jsonl | Original model trained on mixed reflection and expert examples |

Each method starts independently from the same original model and uses the same expert source. Alternative actions and reflections should normally be generated by the original model being trained. The configuration template uses Qwen/Qwen3-32B in non-thinking mode, but another model can be configured. Report stronger-teacher generation as a separate experimental condition.

A state contains Agent-visible conversation history and tool schemas. Alternatives execute in independent deep copies of the same complete ExecutionContext. IWM uses a separate world-model prompt and an `Observation:` target. SR uses real action outcomes to generate a `<reflection>...</reflection>` prefix followed by the expert action; only the action is executed at inference. All methods share the policy input and action format.

K defaults to 3. Each state contributes one expert transition and K alternative transitions. Actual tool execution errors remain IWM supervision. Invalid model output or insufficient alternatives cause explicit failure rather than fabricated data or silent replacement.

## 1. Installation

```bash
git clone https://github.com/weikai202/experiment_kai.git
cd experiment_kai/EarlyExperience/toolsandbox
uv sync --frozen
uv run pytest -q
uv run ee-toolsandbox --help
```

Python 3.10 is required. ToolSandbox is pinned to commit `165848b9a78cead7ca7fe7c89c688b58e6501219`. Runtime dependencies are locked in uv.lock and do not include toolsandbox-pipeline.

## 2. Configure models and splits

Copy `configs/run.example.json` and configure four services:

- `expert`: generates demonstrations; an existing action file supplied through --experts can replace it.
- `generator`: generates alternative actions and reflections, normally using the original model being trained.
- `policy`: serves the original or trained checkpoint during evaluation.
- `user`: the ToolSandbox user simulator; the example uses gpt-4o-mini-2024-07-18.

Each service specifies base_url and api_key_env. Credentials are read from the runtime environment, never embedded in configuration JSON. Qwen and the user simulator may use separate services. Where configured, enable_thinking=false and seed are passed to the server; thinking content causes failure. Proposal and reflection temperature is 0.7; policy temperature is 0.

Provide an independent `manifest.json`, using configs/manifest.example.json as a template:

```json
{
  "train": [{"id": "YOUR_TRAIN_SCENARIO_ID", "family": "YOUR_TRAIN_FAMILY"}],
  "dev": [{"id": "YOUR_DEV_SCENARIO_ID", "family": "YOUR_DEV_FAMILY"}],
  "test": [{"id": "YOUR_TEST_SCENARIO_ID", "family": "YOUR_TEST_FAMILY"}]
}
```

No separate pipeline manifest is required. Use the same split for all three methods. A task and its augmentation variants must remain in one split. Validation detects duplicate IDs, cross-split families, and leakage through known augmentation suffixes. Example IDs are placeholders, not actual scenarios. Collection runs train only, and SFT preparation rejects dev/test sources.

## 3. Collect experience

```bash
uv run ee-toolsandbox collect \
  --config configs/run.json --manifest manifest.json \
  --expert-rule fully_successful --output artifacts/collect-train
```

The default fully_successful rule selects entire demonstrations with milestone_similarity=1 and minefield_similarity=0 after the native episode evaluation. All raw transitions and scenario scores remain available; failed sources are not deleted. The explicit alternative --expert-rule all_completed retains all completed demonstrations, but failed model demonstrations are not verified experts. Preparation fails when no expert examples qualify.

Supply existing expert actions with `--experts experts.json`:

```json
{
  "YOUR_TRAIN_SCENARIO_ID": [
    {"action": {"tool_calls": [{"name": "AGENT_VISIBLE_TOOL_NAME", "arguments": {}}]}},
    {"action": {"response": "Message to the user"}}
  ]
}
```

An optional state_hash on each entry verifies the decision state. During online demonstration generation, branches copy the live expert state. During action-file replay, the user simulator may produce a different conversation; strict state_hash checks are recommended. Expert and alternative observations come from actual execution. Reexecuting the expert action on the main trajectory can produce a different remote stochastic result.

Collection calls models and ToolSandbox tools, including external search services when required by selected scenarios. Outputs include transitions.jsonl, run.json, usage.json, native trajectories, results.json, and summary.json. Failed runs have complete=false and cannot pass CLI preparation. Output directories must be new. Automatic resume is not implemented.

## 4. Prepare SFT data

```bash
# IL/IWM only, without generating reflections.
uv run ee-toolsandbox prepare \
  --run artifacts/collect-train --output artifacts/sft-il-iwm

# Generate grounded SR and all three data categories.
uv run ee-toolsandbox prepare --run artifacts/collect-train \
  --reflect-config configs/run.json --output artifacts/sft-all
```

Each JSONL record has the form `{"messages":[...]}`. grounded_records.jsonl preserves the action/observation evidence behind reflections. provenance.json records sources, data hashes, and sample counts. Without SR generation, the reflection file is empty; SR training rejects empty data. Inspect generated reflections manually: valid formatting does not establish reasoning quality.

## 5. Train

ToolSandbox's older transformers dependency cannot read the cached newer Qwen3 tokenizer. Use a separate training environment:

```bash
uv venv --python 3.10 .venv-train
uv pip install --python .venv-train/bin/python -r requirements-train.txt
uv pip install --python .venv-train/bin/python --no-deps -e .

uv run --no-project --python .venv-train/bin/python python -m ee_toolsandbox.training \
  --method il --model /absolute/path/base-model --data artifacts/sft-all \
  --output checkpoints/il --bf16

uv run --no-project --python .venv-train/bin/python python -m ee_toolsandbox.training \
  --method iwm --model /absolute/path/base-model --data artifacts/sft-all \
  --output checkpoints/iwm --bf16

uv run --no-project --python .venv-train/bin/python python -m ee_toolsandbox.training \
  --method sr --model /absolute/path/base-model --data artifacts/sft-all \
  --output checkpoints/sr --bf16
```

Download the base model separately and replace `/absolute/path/base-model` with its local directory. A prior tokenizer-only check used Qwen3-32B revision `9216db5781bf21249d130ec9da846c4624c16137`; its result is recorded in `validation/qwen_tokenizer_validation.json`. Model weights are not included. Full weight-content hashes, the GPU training stack, and memory requirements have not been validated.

Training uses full-parameter SFT. Defaults are one epoch per stage, learning rate 2e-5, batch size 1, gradient accumulation 32, and seed 0. These are configurable starting points, not paper-validated ToolSandbox hyperparameters. Only the final assistant completion contributes to the loss. History and padding are masked; overlength examples fail instead of being silently truncated. Models load from local files only, without automatic downloads.

The final serving checkpoint is checkpoints/<method>/policy. IWM warm-up is also saved to checkpoints/iwm/iwm. SR contains more training data, so equal epochs do not imply equal training tokens or compute. Report training costs separately.

## 6. Evaluate independently

Serve each trained checkpoint through an OpenAI-compatible inference service, then set policy.model and its endpoint in that method's configuration. Keep the user simulator, split, and sampling settings consistent.

```bash
uv run ee-toolsandbox evaluate --config configs/eval-il.json \
  --manifest manifest.json --split dev --output artifacts/eval-il-dev

# Final evaluation after settings are fixed; use separate configurations and outputs for IWM/SR.
uv run ee-toolsandbox evaluate --config configs/eval-il.json \
  --manifest manifest.json --split test --output artifacts/eval-il-test
```

Evaluation directly calls native Scenario.play_and_evaluate and requires no coordinator from another project. summary.json reports mean_similarity and category metrics; results.json preserves milestone/minefield scores and turn_count. Do not present similarity as a binary success rate. Failed scenarios are not silently skipped to produce a score. A fixed seed does not freeze remote services or wall-clock time; strict replay is not claimed.

This distribution contains only the standalone EarlyExperience implementation. Historical pipeline alignment code and generated experiment artifacts are not included. Data must use the current standalone format; action-envelope-v2 data from the historical integration is incompatible.
