# Implementation Details

**Pipeline overview.** We use the same generation-based evolution pipeline for ToolSandbox, tau3, and BFCL. Generation $G_0$ is initialized from benchmark-public tool or function schemas, with seed Skills encoding tool applicability, preconditions, and reusable action guidance. Each of three rounds executes one disjoint training shard with a fixed generation, collects native trajectories and evaluator outcomes, performs offline memory and Skill updates, validates Skill candidates on a deterministic Dev Mini-Bench, and atomically publishes the next generation. This yields $G_0\rightarrow G_1\rightarrow G_2\rightarrow G_3$. Final comparisons evaluate the Vanilla agent, $G_0$, and $G_3$ on the same frozen test manifest.

**Online decision pipeline.** At each turn, the adapter constructs a compact state from the conversation and tool results visible to the agent. It independently retrieves Policy memory and Skills from the active generation; when Critic evaluation is invoked, an action-conditioned query retrieves World memory. Retrieval uses OpenAI `text-embedding-3-small` with $k=3$ for each resource type. The Initial Policy emits one assistant message, tool call, or benchmark-valid parallel call batch. A deterministic Controller validates tool availability, schema conformance, argument grounding, prerequisites, and parallel independence. The Critic then evaluates the proposal using Controller evidence. With revision budget $r=1$, a single Revision may reuse the original state and retrieved resources, after which the Controller validates the revised action before native execution. Thus, model predictions remain separate from actual environment state, and only validated calls reach the executor.

**Offline evolution.** Native outcomes drive memory and Skill updates. The memory path projects each eligible training trajectory into a sanitized Policy or World view, generates at most one candidate, and applies a duplicate-and-grounding review before `ADD`, `MERGE`, or `SKIP`. The Skill path attributes executed actions to selected Skills, updates success/failure statistics, and maintains a bounded reusable failure-mode buffer. A Skill becomes eligible for rewriting after $m_{\min}=10$ evaluated uses when its empirical failure rate is strictly greater than $\rho=25\%$. Rewriting uses the current Skill, accumulated statistics and failure modes, relevant current-round trajectories, and public schemas. Each candidate is compared with its previous version through paired native executions matched by tool dependency, with every other state, simulator, model, and generation resource shared. Acceptance follows each benchmark's native success criterion, using native reward or similarity for tie-breaking where applicable. Accepted memory and Skill versions enter the next generation.

**Benchmark adapters and splits.** ToolSandbox uses nominal scenario families as split units, keeping all eight augmentation variants together. With seed 0, 129 families are divided into 79/25/25 train/Dev/test families, or 632/200/200 scenarios; the training shards contain 216, 208, and 208 scenarios. The adapter retains the native roles, execution environment, and similarity evaluator, with `gpt-4o-mini-2024-07-18` as user simulator. For tau3, we use the Airline, Retail, and Telecom text domains: 144 tasks form the evolution set, 34 form Dev, and the official 100-task test set is preserved. Each round contains 8 Airline, 20 Retail, and 20 Telecom tasks and uses the native policies, tools, user simulator, and reward evaluator. For BFCL v4, each family joins the index-aligned Base, Miss-Function, Miss-Parameter, and Long-Context variants. The 200 families are split into 120/40/40 train/Dev/test families; each round processes 40 families, or 160 cases. BFCL calls are parsed with Python AST and `literal_eval`, executed in the official stateful simulator, and scored by the official checker and irrelevance checker.

**Models, hyperparameters, and compute.** Policy, Critic, Revision, memory, and Skill-generation calls use `Qwen/Qwen3-32B` served through vLLM in BF16, with temperature 0, seed 0, and `chat_template_kwargs={"enable_thinking": false}`. ToolSandbox and tau3 use GPT-4o-mini for user simulation, while retrieval uses `text-embedding-3-small`. Role-specific output limits are calibrated from training-only smoke traces, rounded to multiples of 64, and frozen with the prompt, schema, tokenizer, model, and dataset hashes. Experiments run on $2\times$ NVIDIA H100 GPUs. The default setting is three evolution rounds, $m_{\min}=10$, $k=3$, $r=1$, and $\rho=25\%$. The accompanying sensitivity study varies one factor at a time: rounds over $\{0,1,2,3,4,5\}$, $m_{\min}$ over $\{5,10,15,20,25\}$, $k$ over $\{1,2,3,4,5,6\}$, $r$ over $\{0,1,2,3\}$, and $\rho$ over $\{10\%,25\%,40\%\}$, reporting Action Recall and relative cost.

**Accounting and reproducibility.** Every model request, physical attempt, accepted application, environment effect, and generation update is durably identified and checkpointed. Round latency spans the first online dispatch through native evaluation, offline evolution, generation publication, and the final checkpoint. Relative cost is normalized to the default setting and counts only Qwen output tokens causally linked to committed memory or Skill effects; rejected, `NONE`, `SKIP`, retry-only, and no-op outputs contribute zero. Recovery preserves completed manifest prefixes and reconciles in-flight operations before resuming.
